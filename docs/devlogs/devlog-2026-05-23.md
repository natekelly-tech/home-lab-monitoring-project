## What Was Accomplished

### System Interrogation -- k3s Datastore Identification

Reconnected to EC2 after a two-week gap. First task was determining the k3s datastore backend before designing any backup procedure, since the backup method differs significantly between SQLite and embedded etcd.

Ran `sudo systemctl status k3s` and confirmed the process command is `/usr/local/bin/k3s server` with no `--cluster-init` or `--datastore-endpoint` flags, meaning k3s launched with defaults. Confirmed the presence of `kine.sock` in `/var/lib/rancher/k3s/server/`, which identifies the Kine embedded SQLite compatibility layer. Kine presents an etcd-compatible interface to Kubernetes but stores state in a single SQLite file. The COMPACT log messages visible in systemctl output are Kine mimicking etcd compaction behavior against the SQLite backend.

Confirmed database location at `/var/lib/rancher/k3s/server/db/`:

```
state.db       3.1 MB   main database file
state.db-shm   32 KB    shared memory index
state.db-wal   4.5 MB   write-ahead log
```

SQLite is running in WAL mode. All three files constitute the complete cluster database. Backing up only `state.db` while k3s is running produces an inconsistent snapshot because committed transactions in the WAL file would be missing. Correct backup procedure uses the SQLite online backup API (`sqlite3 state.db ".backup /path/to/backup.db"`) which handles WAL consistency atomically without stopping the cluster.

### System Interrogation -- Application Statefulness Check

Confirmed the application layer is fully stateless via three checks. Grep analysis of `backend/app/` source returned no `open()` calls with write modes, no `write()` calls, and no sqlite or database references. `kubectl get pvc` and `kubectl get pv` both returned no resources. The application performs live HTTP checks on every request and returns the result immediately. Nothing is written to disk. This means there is no application data to back up regardless of backup frequency, and restoration of the application layer is entirely a matter of running the container again.

## Decisions Made

### SQLite online backup API instead of stop-and-copy
Stopping k3s to take a consistent copy of state.db is the simplest approach but introduces downtime. The SQLite online backup API (`sqlite3 state.db ".backup /path/to/backup.db"`) handles WAL consistency atomically while the cluster is running. For a production system with a 24-hour RPO this is the correct choice. The online backup approach is scheduled for implementation as a cron job in Session 2.

### Full backups for state.db export, not incremental
The state.db plus WAL files total approximately 8 MB. At that size incremental or differential adds complexity with no meaningful time or cost saving. A full copy on every backup run is simpler, faster to restore, and easier to verify. Complexity is the enemy of a working backup system.

### S3 in us-east-1 satisfies off-site requirement
Traditional 3-2-1 implies physical media for the off-site copy. For a cloud-native system at LOW impact classification, a different AWS region with a separate failure domain satisfies the intent. us-east-1 and us-west-1 share no physical infrastructure. This decision is documented and accepted in the Backup Plan.

### docx files excluded from git via .gitignore
Formal documents (SSP, Backup Plan) are submitted to Dollahite via Sakai, not via the public GitHub repo. Binary Word documents do not diff cleanly and have no place in a public repo. Added `docs/*.docx` to .gitignore.
